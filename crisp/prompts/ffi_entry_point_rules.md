The code contains two kinds of functions: implementation functions and FFI entry points. A function is an FFI entry point if it has the `#[no_mangle]` or `#[export_name]` attribute ("export attributes"). Note that just having `unsafe extern "C"` qualifiers without export attributes does NOT make a function an FFI entry point. All functions without export attributes are implementation functions. Implementation code may be freely refactored to improve safety. For FFI entry points, the following rules apply and must never be changed or broken:
- You must not change the signature. FFI entry point signatures must remain exactly as-is to ensure ABI compatibility with the current version of the code. Don't remove `unsafe` or `extern "C"` qualifiers from FFI entry points.
- For struct types that appear only behind a pointer, you may assume the struct is opaque to the user of the library (unless otherwise indicated within the code itself), as is considered best practice in C. This means the struct layout is not part of the ABI, so you may freely change the field types to improve safety.
- FFI entry points adapt the C interface to named Rust implementation functions. They may validate inputs, convert raw pointers into justified references or bounded views, project fields, assemble argument views, dispatch, and convert results back to C types.
- Necessary adaptation may include null checks and calls to named validation or view-construction helpers. Every conversion must preserve the required initialization, extent, aliasing, and lifetime guarantees. Boundary placement does not excuse an unjustified conversion.
- When creating all views before dispatch would violate aliasing or observation order, the entry point may supply invocation-local access closures. These closures may construct the requested views and invoke the supplied operation. Named safe implementation code must determine whether, when, and in what order those accesses occur.
- Program logic must remain in named implementation functions: algorithmic decisions, traversal and copy loops, status policy, allocation and cleanup, and sequencing of observable effects. Moving such logic into an entry point, macro, or boundary closure violates this rule.
- An increase in unsafe operations inside an entry point is a review trigger, not an automatic violation. Review must distinguish necessary boundary adaptation from relocated program logic. A rejection must identify the specific misplaced operation or unmet safety obligation; increased counts or wrapper length alone are insufficient.
- For example, a wrapper may supply deferred conversion of an optional C string while a named safe implementation decides whether and when to request it. A buffer-transfer wrapper may supply scoped source and destination views while a named safe implementation calculates ranges, controls copy order, performs copies, and publishes results. The wrapper must not choose transfer ranges, loop over transfers, copy bytes, or decide publication order, including inside its access closures.
- Don't hide implementation logic in macros. Macro expansions count as part of the FFI entry point body: an entry point must dispatch to a named implementation function, and must not invoke macros that expand to program logic or unsafe code.
- Don't add calls to FFI entry points (`*_ffi` functions), and don't use them as function-pointer values (e.g. don't assign an FFI entry point as a default callback or store it in a function-pointer field -- use the corresponding implementation function instead).  These entry points are only for use from C.  When changing a non-FFI function's signature, you should update all call sites to handle the new signature, rather than changing some call sites to call the FFI entry point that still has the old signature.
